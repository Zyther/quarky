# Phase 2: Tab5-Native 2.4GHz WiFi/BLE Suite — Design

**Status:** Draft for review
**Date:** 2026-08-06
**Depends on:** Phase 1 Foundation (`2026-08-06-tab5-foundation-design.md`) — `IRadio` (esp-hosted WiFiRemote), `FeatureRegistry`, LVGL shell/launcher, `lv_keyboard` text-input pattern.
**Scope:** Every WiFi and BLE feature that the ESP32-C6 co-processor can do natively (2.4GHz only — 5GHz is Phase 6, on a separate C5 satellite), running entirely on the Tab5 with no Cardputer-ADV involvement.

### Explicitly out of scope for Phase 2
- BLE-based nRF52 features (Poseidon's `nrf52_hw.cpp` suite) — that's a different satellite hardware concept not part of this program's device inventory.
- 5GHz anything — Phase 6.
- Network-layer attacks riding on top of an established WiFi connection (Responder, SSDP, DHCP starvation, MITM, port scanning) — these aren't radio-specific; bundled into Phase 7's sweep since they're closer to "network toolkit" than "WiFi radio feature."

## 2. Architecture

### 2.1 Module Structure

Each feature becomes one `FeatureModule` (per the Phase 1 contract) with `Affinity::TAB5_NATIVE`, living under `firmware/tab5/src/features/wifi/` or `firmware/tab5/src/features/ble/`. One file per feature, matching the donor codebases' one-module-per-file convention (Bruce's `src/modules/wifi/*.cpp`, Poseidon's `src/features/*.cpp`) rather than consolidating — keeps each feature's diff isolated and matches the "files that change together live together" principle, since WiFi and BLE features here don't share implementation logic beyond the common `IRadio` and UI patterns.

```
firmware/tab5/src/features/
├── wifi/
│   ├── wifi_scan.{h,cpp}
│   ├── wifi_deauth.{h,cpp}
│   ├── wifi_evil_portal.{h,cpp}
│   ├── wifi_karma.{h,cpp}
│   ├── wifi_beacon_spam.{h,cpp}
│   ├── wifi_pmkid.{h,cpp}
│   ├── wifi_spectrum.{h,cpp}
│   ├── wifi_ciw.{h,cpp}
│   └── wifi_common.{h,cpp}       # shared AP-list model, channel-hop helper
└── ble/
    ├── ble_scan.{h,cpp}
    ├── ble_spam.{h,cpp}
    ├── ble_bad_kb.{h,cpp}
```

### 2.2 UI Pattern

Each feature screen follows the Phase 1 reference patterns directly:
- List-output features (scan, sniffer, finder, clone-candidate list) use an `lv_list` or `lv_table` widget, tap-to-select-target where relevant.
- Parameter-entry features (evil portal SSID, beacon spam SSID list, target BSSID) use `lv_textarea` + `lv_keyboard`, the exact pattern proven in Phase 1 Task 8.
- Long-running/streaming features (spectrum analyzer, sniffer, flood) show a live-updating chart (`lv_chart`) or scrolling log (`lv_textarea` in read-only mode), with a persistent Stop button.
- Every feature screen is reachable from the WiFi or BLE category tile in the Phase 1 launcher grid (`Shell::build`'s per-category loop already supports this — Phase 2 just needs to register enough modules for the WiFi/BLE categories to populate).

### 2.3 Capture File Handling

PMKID/handshake captures and BLE sniffer CSVs write to the Tab5's SD card (Phase 1 Task 10's `IStorage`/`StorageSD`), using the same directory convention as Bruce (`/BruceRF`-style top-level folders) adapted to `/quarky/captures/wifi/` and `/quarky/captures/ble/`. No new bulk-transfer protocol work needed here — these files stay local to the Tab5 that captured them; the C2 bulk channel (Phase 1) is for satellite-originated captures (Phase 4+), not Tab5-native ones.

## 3. Risks / Open Questions

- **Deauth frame injection through esp-hosted is unverified.** Poseidon's and Bruce's deauth capability both depend on bypassing a local `libnet80211.a` sanity check via a linker-time symbol override — a trick that assumes the WiFi stack is linked directly into the firmware image. Under esp-hosted, the actual 802.11 stack runs on the *C6*, with the P4 only issuing RPC calls through WiFiRemote. Whether raw/malformed frame injection (deauth, beacon spam with arbitrary source MAC, EAPOL manipulation) is exposed through esp-hosted's RPC surface at all is unconfirmed and is the single biggest risk in this phase. **First task of Phase 2's implementation plan should be a spike**: attempt a basic raw deauth frame send through `esp_wifi_80211_tx()` (or equivalent) over WiFiRemote and confirm it reaches the air, before committing to porting the rest of the attack suite on this assumption.
- **BLE HID (Bad-BLE) over esp-hosted** — same category of risk as above but for BLE instead of WiFi: needs confirmation that NimBLE-Arduino's HID profile support functions correctly when BLE is running on a remote C6 rather than a local radio.
- **Promiscuous-mode packet capture** (client scan, PMKID/handshake capture, sniffers) needs `esp_wifi_set_promiscuous()` and a raw-frame RX callback — same RPC-surface question as deauth.
- If any of the above prove unsupported through WiFiRemote, the fallback is to run that specific feature on the Cardputer-ADV instead (it has a native, non-hosted ESP32-S3 radio) and treat it as a `CARDPUTER_ADV`-affinity remote feature rather than `TAB5_NATIVE` — the Phase 1 feature-contract split already supports this without any architecture change, just a different `Affinity` value per module.

## 4. Testing Strategy

- Host-native tests for anything with pure logic independent of the radio: AP-list data structures, OUI vendor-DB lookup, CIW payload table integrity, PMKID/handshake file-format writers.
- On-device verification for every feature against real target hardware (a test AP/router you control, a spare phone for BLE targets) — this phase is fundamentally about radio behavior that can't be meaningfully unit-tested.
- The Phase 2 implementation plan should open with the esp-hosted raw-frame-injection spike (Risks section) as its first task, since a negative result there reshapes the rest of the plan's task list before more work is sunk into porting attack logic that may need to move to Cardputer-ADV instead.

## 5. Definition of Done

1. Esp-hosted raw-frame-injection spike resolved (pass → proceed as planned; fail → replan affected features onto Cardputer-ADV).
2. Every feature in Section 1's tables is either working on real hardware, or explicitly re-scoped to Cardputer-ADV with a note in this doc's Risks section.
3. Capture files (PMKID, handshakes, BLE sniffer CSV) verified readable by standard external tools (hashcat for handshakes/PMKID, Wireshark for pcap) — not just self-consistent with our own writer/reader.
4. All WiFi/BLE launcher tiles present and functional from the Tab5 UI with no Cardputer-ADV connection required.
