# RF433

Tab5-native 433MHz OOK/ASK sub-GHz tooling (RF433 category, launcher tab
"RF433"). Interrupt-driven edge-timing capture on receive, bit-banged
`digitalWrite()`/`delayMicroseconds()` transmit -- no dedicated sub-GHz radio
chip, just the RF433 receiver/transmitter unit's data pins driven directly.
Two launcher tiles: **RF433 Scan/Capture** (capture, replay, decode, export)
and **RF433 Bruteforce** (fixed-code keyspace sweep). A third component,
replay, has no tile of its own -- it's reachable only from buttons on the
other two screens.

## Shared hardware: one physical pin, arbitrated

Both the RF433 receiver and transmitter pins are the *same* physical GPIO
(GPIO53), which is also the SDA line of the HY2.0 PORT.A connector's I2C bus
(shared with the NFC/RFID2 units) and one of the IR unit's pins. A runtime
arbiter (`Gpio53Arbiter`) ensures only one of these subsystems owns the pin
at a time:

- If an NFC/RFID2 screen currently has PORT.A claimed, starting a capture or
  a replay is refused outright -- close that screen first.
- Receive and transmit are also mutually exclusive with **each other** (an
  explicit check layered on top of the arbiter, since both are the same
  "owner" from the arbiter's point of view): a capture in progress refuses a
  replay, and a replay in progress refuses a capture start.

Every refusal is reported through the screen's own status text rather than
silently doing nothing -- if a button appears to do nothing, check the
status line for why.

## RF433 Scan/Capture

The main working screen (`rf433_scan.cpp`): capture live signals, replay
them, decode them, export them, or load a signal from SD.

### Capturing

1. Open **RF433 > RF433 Scan/Capture**.
2. Tap **Start Capture**. The status line shows `Status: Capturing
   (GPIO53)...`. An interrupt handler timestamps every edge on the RF433
   receive pin; edges are grouped into "bursts" separated by silence gaps
   longer than 25ms (chosen to sit clearly outside the 8-15ms repeat cadence
   of real fixed-code remotes, so one held button press's repeated bursts
   stay merged into a single captured signal).
3. Each finalized burst appears in the list as `Sig #<id>: <n> edges, ~<ms>
   ms (@<s> s)`, and is also written unconditionally to
   `/quarky/captures/rf433/sig_<ms>_<edges>.raw` on SD (best-effort; a
   missing/unmounted SD card doesn't stop the capture, just skips that
   file).
4. Tap **Stop Capture** to end the session. Stopping mid-burst discards
   whatever was still accumulating -- a burst you cut off isn't saved as a
   partial signal.

**Limits, disclosed and real:** at most 16 signals are kept in the
in-session list -- the 17th evicts the oldest. Each signal is capped at
8192 edges; a burst that runs longer has its tail dropped and is marked
`[truncated]` in the list (replay still works off the captured prefix). A
burst shorter than 10 edges is treated as noise and discarded silently. If
the capture hardware itself hits a hard 100,000-edge-per-session ceiling
(a runaway-interrupt guard, not a normal-use limit), the status line shows
`Capture overrun -- check antenna/pin` and capture stops automatically.

### Acting on a captured (or loaded) signal

Tap a row to select it (a tap alone never transmits). With a signal
selected, three buttons act on it:

| Button | Effect |
|---|---|
| **Replay Selected** | Bit-bangs the selected signal's edge timing back out on the transmit pin (see [Replay](#replay), below) |
| **Decode Selected** | Runs protocol decoding against known fixed-code formats; shows `Decoded: <protocol> code=0x<hex> (<n> bits)` on a match, or `No known protocol matched` otherwise |
| **Save as .sub** | Writes the signal as a real Flipper Zero-compatible `.sub` RAW file to `/quarky/captures/rf433/sub/capture_<id>.sub` |

**Select** toggles a *separate* multi-select "chain" mode: while on,
tapping rows adds/removes them (in tap order) from a chain instead of
setting the single Replay/Decode/Save selection. **Combine -> .sub**
concatenates up to 8 chained signals' real edge timing (each segment's own
internal timing preserved, joined by the same 25ms gap convention) into one
`.sub` file at `/quarky/captures/rf433/sub/chain_<first-id>.sub`.

**Load from SD (.sub)** opens a file picker over
`/quarky/captures/rf433/sub/` for `.sub` files (this is a separate
directory from the automatic per-burst `.raw` dumps above, specifically so
a large capture history never buries a `.sub` file the picker can't reach).
A loaded file has its own **Replay Loaded** button, sharing the exact same
transmit engine as Replay Selected -- only one transmit can be in flight at
a time regardless of which button started it.

**Clear** empties the live-capture list only; it does not touch a loaded
SD file, and does not stop an in-progress capture.

## RF433 Bruteforce

Fixed-code keyspace sweep (`rf433_bruteforce.cpp`): transmits every
possible code for a selected protocol, one at a time.

1. Open **RF433 > RF433 Bruteforce**.
2. Pick a protocol from the dropdown (defaults to **Nice 12bit**):

| Protocol | Bits | Codes | Notes |
|---|---|---|---|
| Came 12bit | 12 | 4096 | |
| Nice 12bit | 12 | 4096 | Default |
| Ansonic 12bit | 12 | 4096 | |
| Holtek 12bit | 12 | 4096 | |
| Linear 10bit | 10 | 1024 | |
| Chamberlain 9bit (unverified encoding) | 9 | 512 | **Known-suspect**: this table row is byte-for-byte identical to the Holtek row rather than real Chamberlain/DIP-switch timing (a real Chamberlain uses a structurally different 4-bit-symbol encoding this project's own decoder expects). A candidate generated for this entry will likely not be recognised by real Chamberlain hardware -- included with the caveat rather than removed, since it's a faithfully-ported (if seemingly mislabeled) donor value, not an invention |

3. Point the transmitter at the target and tap **Start**. Status shows
   `Running <protocol>: code <n> / <total>` with a progress bar; the
   protocol dropdown disables while running. Every code transmits via the
   same replay engine RF433 Scan/Capture uses (one candidate signal
   synthesized and sent per poll tick, waiting for the previous transmit to
   finish first).
4. Tap **Stop** to cancel at any point, or let it run to completion.

A full 12-bit sweep (4096 codes) runs continuously until stopped or
complete; the donor tooling this was ported from measured roughly 50ms/code,
so a full 12-bit sweep is on the order of a few minutes. If the transmit
engine ever refuses mid-sweep (most likely: something else claimed GPIO53,
e.g. an NFC/RFID2 screen was opened while the sweep was running), the sweep
stops itself and reports the real refusal reason rather than silently
retrying the same code forever. Leaving the screen while a sweep is running
also stops it -- a multi-minute transmit sweep is not left running silently
in the background.

## Replay

Not a launcher tile -- reached only via **Replay Selected** / **Replay
Loaded** (RF433 Scan/Capture) or automatically by RF433 Bruteforce, all of
which share this one transmit engine (`rf433_replay.cpp`).

Transmitting reproduces a signal's captured edge timing via
`digitalWrite()`/`delayMicroseconds()` on a dedicated background task (a
single burst can legitimately take hundreds of milliseconds, too long to
run synchronously on the UI's own task). Only one transmit can be in
flight at a time; a second Replay tap while one is already running does
nothing but log a refusal.

**Truncated signals are replayed, not refused.** Since truncation only ever
drops the *tail* of a real capture, the recorded prefix is still played
back -- the UI shows `Replay: Transmitting... [TRUNCATED -- partial burst
only]` (and `Replay: Done [TRUNCATED...]` afterward) so it's clear the full
original burst wasn't reproduced, rather than silently pretending it was.

Every other refusal (an RX capture is currently active, the signal has no
edges at all, GPIO53 is held by an NFC/RFID2 session, or the background
task itself failed to start) surfaces via the same status label as
`Replay: Failed (<reason>)`.
