## What this phase built

Real feature logic for all four of the Tab5's HY2.0-connector peripherals, replacing Phase 1's detection-only HAL:

- **NFC unit (ST25R3916, I2C 0x50):** a from-scratch polled-register ISO14443-A reader driver (`features/nfc/st25r3916_driver.{h,cpp}`) — chip-ID readback, field on/off, WUPA→anticollision→SELECT tag detection, a full ISO14443-4/EMV APDU layer (RATS + I-block + BER-TLV), and a Listen Mode (card-emulation) driver reusing saved tag UID/ATQA/SAK.
- **RFID2 unit (WS1850S, I2C 0x28):** an MFRC522/PN512-family register driver (`features/nfc/ws1850s_driver.{h,cpp}`), MIFARE Classic key recovery (dictionary/nested/static-nested/parity-oracle-dictionary), NTAG21x (Amiibo-class) read/write.
- **RF433R/T (GPIO53, OOK/ASK):** interrupt-driven edge capture, scan, replay, brand/protocol decode (7 brands), fixed-code bruteforce, and Flipper `.sub` file interop.
- **IR unit (M5Stack "Unit IR" SKU U002, plain GPIO on the same PORT.A pins):** RMT-based transmit, TV-B-Gone (271-code Gen3 NA/EU database), raw capture ("IR Learn"), a real Flipper-IRDB folder navigator with NEC/NECext protocol encoding, and a jammer.
- **Shared infrastructure:** an SD-backed NFC tag library (save/load/browse), a generic SD file browser, a real GPIO53 three-way runtime arbiter (`hal/gpio53_arbiter.{h,cpp}`), and a real battery HAL (INA226 @ 0x41).

## Architecture decisions worth knowing

**Two "NFC-family" units, two unrelated chips, two from-scratch drivers, one shared UI layer.** Phase 1-era docs assumed both units were PN532-based. Neither is: the NFC unit is an **ST25R3916** (own register map, no donor-project precedent at all — Bruce/Poseidon/UniGeek only have PN532 code) and RFID2 is a **WS1850S**, which is MFRC522/PN512-register-compatible, *not* PN532 (confirmed on real hardware: `VersionReg (0x37) = 0x15`, and a real PN532 `GetFirmwareVersion` frame sent to the same address got no response — Task 3). `nfc_read.cpp`/`nfc_common.cpp` share UID formatting and result-card UI across both units, but dispatch to two genuinely separate low-level drivers underneath, exactly as the corrected spec's Section 2.1 calls for.

**RFAL (ST's own reference driver) cannot be used on this hardware, at all.** The Tab5's HY2.0 connector has no IRQ line (GND/5V/SDA/SCL only, confirmed in Task 2). ST's vendored RFAL library's I2C-mode constructor requires an IRQ pin and every transceive/interrupt path in it uses `digitalRead(int_pin)` as its only completion signal — an architecture mismatch, not a parameter bug. Cursor's original (unreviewed) Task 4 attempt tried to use RFAL anyway and was non-functional by construction; this project's own review caught it and the fix was to remove the RFAL dependency entirely and build a real polled-register ISO14443-A implementation directly against the same primary sources (ST's DS12484 Rev 3 datasheet + the pinned RFAL reference driver commit, ~40 citations independently spot-verified with zero substantive mismatches). Every later NFC-unit feature (EMV/Task 13, Listen Mode/Task 24) extends this same polled-register driver the same way, never RFAL.

**GPIO53/54 is a three-way shared resource, arbitrated at runtime, not just by convention.** External I2C (both NFC-family units), RF433R/T, and the IR unit all use the same two physical pins on the Tab5's single HY2.0 PORT.A connector. Phase 1/early-Phase-3 treated this as a documented convention (cross-referencing comments in three files); once NFC and RF433 both got persistent launcher screens (Tasks 4-5) this became live-reachable and needed a real interlock. `hal/gpio53_arbiter.{h,cpp}` (`Owner::kNone/kExternalI2c/kRf433/kIr`, claim/release, refuse-rather-than-steal) was built as a cross-cutting fix (not a numbered plan task) once this became load-bearing, and every subsequent PORT.A consumer (RF433 transmit/Task 6, the IR HAL/Task 15) claims/releases through it.

**RF433 transmit/synthesis always goes through one reviewed transmit path.** `Rf433Replay::transmit()` (Task 6) runs the bit-bang loop in a dedicated, core-pinned FreeRTOS task (mirroring `wifi_connect.cpp`'s established pattern) with real RX/TX mutual-exclusion against `Rf433Common`'s capture side. Task 8 (bruteforce) deliberately synthesizes each candidate as a `CapturedSignal`/`EdgeSample` array and calls this same `transmit()` rather than reimplementing raw bit-banging — so every RF433 transmit path, live or synthesized, inherits the same safety machinery (GPIO53 arbiter, core pinning, RX/TX exclusion) instead of each feature reinventing it.

**IR is plain GPIO, not I2C — a hardware-identity correction with real downstream consequences.** CLAUDE.md and this phase's own spec originally assumed a dedicated I2C IR transceiver chip. The real M5Stack "Unit IR" (SKU U002) is a 4-wire HY2.0 unit: TX is a bare transistor + 940nm LED (GPIO53), RX is an IRM-3638T carrier-demodulating receiver module with a digital output pin (GPIO54) — no register interface, nothing to "identify" the way Task 2 identified the NFC unit's chip ID. This makes the IR unit the **third** real consumer of GPIO53/54, alongside external I2C and RF433 (Task 15 added `Owner::kIr` to the arbiter ahead of the rest of its own implementation for exactly this reason). IR transmit and receive both use the ESP32-P4's RMT peripheral (`esp32-hal-rmt.h`) rather than bit-banging, deliberately claiming/releasing the arbiter around `rmtInit()`/`rmtDeinit()` instead of composing with the plain-GPIO HAL, since RMT reassigns the pin's peripheral-manager ownership itself.

**WiFi C2 became lazy/opt-in as a direct consequence of Phase 3's own hardware findings.** Investigating a real crash in Task 18 (IR Clone) traced to esp-hosted's WiFi/BLE-over-SDIO transport consuming ~180KB of the Tab5's ~187KB total DMA-capable memory pool at boot — a pre-existing Phase 1/2 architectural fact, not something Phase 3 introduced, but one Phase 3's own SD-heavy IR/RF433 features were the first to collide with in practice. `C2LinkWifi::init()` is no longer called unconditionally at boot; BLE C2 is now the default transport, with an explicit "Enable WiFi Link" button on the pairing screen for opt-in WiFi C2. This is also the first real, evidence-backed data point for the project owner's separately-tracked "C5 companion rescope" consideration (moving softAP/WiFi-server features off the Tab5 entirely) — mentioned here as forward-looking context only; that rescope itself is not decided or in scope for this phase.

## Real hardware findings (root causes, not just "fixed a bug")

**GPIO53 pin-ownership conflict (Task 2).** `main.cpp`'s boot sequence called `rf433.init()` unconditionally, which reconfigured GPIO53 as a digital output — clobbering the external I2C bus's SDA line on every single boot regardless of which physical unit was actually connected. Root-caused by tracing the real framework mechanism: `pinMode()` on an I2C-owned pin goes through `perimanSetPinBus()`, which invokes the previous owner's deinit callback (`i2cDetachBus()` → `i2cDeinit()` → `i2c_del_master_bus()`), destroying the entire `Wire1` peripheral object, not just re-routing one pin. Fixed by making RF433's pin claim on-demand only; later formalized into the full three-way arbiter above.

**Wrong chip-family assumptions, found and corrected three separate times.** WS1850S was assumed PN532-compatible (Task 3) — it's MFRC522/PN512-family; confirmed via real donor source (Bruce's `RFID2.cpp`, UniGeek's `MFRC522Screen.cpp`) and on real hardware (`VersionReg = 0x15`, a real PN532 probe getting no response). `ESP-Amiibolink` was assumed to be a straightforward NTAG215 read/write port (Task 11) — it's actually a NimBLE **client** that uploads to a separate external commercial device and contains zero NFC tag I/O; replaced with a port of Bruce's own `RFID2.cpp` NTAG21x read/write logic instead, which was already vendored and already working. The IR unit was assumed to be I2C (Task 15, and CLAUDE.md itself) — a real I2C bus census came back completely empty, which was the *correct* result for hardware that was never I2C; the real datasheet resolved it as plain GPIO.

**RF433 scan crash from unbounded per-tick work (Task 5 review).** `poll()` sampled `micros()` before draining the ISR ring buffer, so an edge landing mid-drain made the idle-gap check's unsigned subtraction underflow to ~4×10⁹ — firing a false idle-timeout (and its expensive SD-write/list-append work) on nearly every tick under real, live 433MHz traffic. Found and fixed before it ever reached hardware, by code inspection during a controller audit of unreviewed (Cursor-authored) work.

**Internal-DRAM bootloop from a static RF433 buffer (real hardware, 2026-08-20).** Flashing Tasks 4-6 together produced a 100%-reproducible bootloop (`spi_flash_disable_interrupts_and_other_cpu` assert) or, on some boots, BLE HCI allocation failures — both symptoms of the same starved internal-RAM pool. Bisected to Task 5's `static CapturedSignal s_signals[16]` (~64-74KB) landing in internal DRAM. Fixed with `heap_caps_malloc(..., MALLOC_CAP_SPIRAM)`; confirmed the "obvious" fix (`EXT_RAM_BSS_ATTR`) would silently no-op in this build since `CONFIG_SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY` is unset in the real framework sdkconfig.

**IR watchdog crash from a blocking test (Task 15).** The first IR bring-up spike ran its whole test (six 500ms `delay()` cycles plus a blocking 10-second RX-poll loop) inline in the serial-command handler, starving `loopTask`'s watchdog feed and rebooting the board mid-test. Fixed by converting to the same `poll()`-driven state-machine pattern every other multi-second RF433/IR operation in this codebase already uses.

**IR carrier-polarity bug, found via three-way cross-donor comparison (Task 16).** TV-B-Gone produced zero response from a real LG TV with zero logged errors on the first attempt. The project owner independently tested two other real implementations against the same TV: Poseidon's own port also failed; UniGeek's port (the *same* 271-code database this project vendors) succeeded — pointing squarely at this project's own transmit path. Root cause, found by reading real ESP-IDF source rather than trusting `esp32-hal-rmt.h`'s misleading doc comment: `rmtSetCarrier()`'s `carrier_level` argument was passed as `true`, inverting the real default (carrier modulated onto "space" instead of "mark"). Fixed; re-tested against the same TV: pass.

**LVGL internal-memory-pool exhaustion (Task 18).** IR Clone's recursive Flipper-IRDB navigator exhausted LVGL's 64KB static internal-RAM widget/style pool after a few stacked real directory levels, crashing either via an unchecked NULL-pointer write inside LVGL's own `lv_draw_sw_fill.c` or an `LV_ASSERT_MALLOC` spin the watchdog eventually aborted. Fixed by raising `LV_MEM_SIZE` to 1MB and moving it to PSRAM; verified via a real stress test (16 stacked 32-row screens) at only 24% pool used.

**O(N²) SD directory scan (Task 18).** A second, unrelated real crash on a much larger IRDB folder (117 subdirectories) traced to Arduino's `openNextFile()` discarding the directory entry's already-known type and `stat()`-ing each entry by path instead — which re-walks the whole FATFS directory per entry. Measured directly: scanning 236 raw entries took 8.70 real seconds against a 5-second watchdog timeout. Fixed by scanning via POSIX `opendir()`/`readdir()` directly, reading the entry type ESP-IDF's own FATFS VFS already provides — verified 60x faster (145ms) with byte-identical real counts.

**DMA-capable memory exhaustion from WiFi/BLE-over-SDIO (Task 18 investigation).** A separate real crash/"missing folders" symptom traced (via a dedicated deep-investigation pass) to esp-hosted's own transport mempool allocator requesting `MALLOC_CAP_8BIT|MALLOC_CAP_DMA|MALLOC_CAP_INTERNAL` for the WiFi/BLE-over-SDIO link to the onboard ESP32-C6 — genuinely DMA-required, not a misrouted small allocation. Measured: `hostedInitWiFi()` alone costs ~128KB, WiFi AP/server bring-up another ~18KB, NimBLE init/host-task another ~33KB, against a ~187KB total DMA-capable pool. The two Kconfig options that could move this to PSRAM (`CONFIG_ESP_HOSTED_MEMPOOL_PREFER_SPIRAM`, `CONFIG_ESP_HOSTED_DFLT_TASK_FROM_SPIRAM`) are both off in the pioarduino framework's prebuilt libs and not changeable from this project's own build flags. This is the real basis for making `C2LinkWifi::init()` lazy/opt-in (see architecture section above) — a structural, pre-existing hardware/framework constraint of this board, not a Phase 3 code defect, but one Phase 3's own SD-heavy features were the first to expose.

**A donor cryptography bug, found and proven, not just asserted (Task 9).** UniGeek's `NestedAttack.cpp`/`StaticNestedAttack.cpp` both cross-check a recovered candidate key against the *second* 32-bit CRYPTO1 keystream word while feeding the *first* word to `lfsr_recovery32()` — rejecting the correct key on every real multi-nonce run. Fixed in this project's own `recover_from_ks()`, with a host-native test proving the fix non-tautologically (recovery genuinely succeeds from the first word, genuinely fails from the second).

**A real LVGL `lv_dropdown` bug, found on real hardware (Task 9 checkpoint).** The MIFARE-crack mode-select dropdown resolved every tap to its last row regardless of where the user actually touched, silently making two of four attack modes unreachable. Root-caused with real touch-coordinate instrumentation (not guessed): a confirmed-correct tap squarely inside "Dictionary"'s real on-screen bounds still resolved to index 3, ruling out this project's own touch/rotation mapping. Fixed by replacing the dropdown with the same plain-checkable-button radio-group pattern already used elsewhere in this codebase. **Not yet independently re-checked**: three other `lv_dropdown` usages elsewhere in this codebase (`wifi_evil_portal.cpp`, `ble_spam.cpp`, `rf433_bruteforce.cpp`) have not been hardware-tested for the same failure and are a disclosed, real, unresolved risk — not assumed fine by association.

**Amiibo tags don't carry a standard NDEF Capability Container (Task 11 checkpoint).** Real Amiibo/NTAG215 tags read `CC=0xFF` at page 3 instead of the expected `0x3E`, because Nintendo's proprietary format overwrites that page. Page count (135, from the real NACK-terminated read loop) was unaffected and both read and write worked correctly regardless — the mismatch was cosmetic (wrong tag-family label only). Fixed with a page-count-based tag-name fallback that doesn't depend on the region Amiibo data overwrites.

## Known limitations / deferred work

**Task 12 (SRIX tag tool) — deliberately deferred, a real scope mismatch, not a failure.** Bruce's donor SRIX code is PN532-specific top to bottom; this project has no PN532 anywhere. A real port would need: (a) ISO14443-B PHY support added to `st25r3916_driver.cpp` (the chip supports it at the silicon level, per ST's own RFAL examples, but this project's driver doesn't implement that layer yet, and — per Task 4's established finding — RFAL itself can't be lifted unmodified onto this hardware's no-IRQ HY2.0 connector, so it would need the same "port RFAL's sequence into polled-register code" treatment Task 2/4 already did once), plus (b) SRIX's own proprietary command layer (INITIATE/SELECT/GET UID/READ BLOCK) on top of that PHY, cited from ST's real SRIX4K datasheet. This is comparable-scope protocol research to Task 24's Listen Mode work, not a "low-effort port" as originally scoped — and there is no real SRIX tag on hand to verify against regardless. Project owner's explicit decision: defer entirely, revisit after every other phase is complete, likely bundled with further 14443-B protocol-mode work.

**Task 13 (EMV/APDU reader) — code-complete, independently reviewed, real-hardware verification still outstanding.** Implementation extended `st25r3916_driver` with `iso14443_4_activate()`/`apdu_transceive()` (RATS + I-block, cited against ST's real RFAL ISO-DEP source) and a new `nfc_emv_read.{h,cpp}` porting Bruce's real APDU/BER-TLV logic (SELECT PPSE → SELECT AID → GPO no-PDOL → AFL walk/READ RECORD). Two real bugs were found and fixed by independent review: a BER-TLV long-form-length integer overflow that could bypass a bounds check via `size_t` wraparound (crafted-length bytes could drive an out-of-bounds stack read), and a missing I-block block-number-match check that would have silently accepted a stale/duplicate response as authoritative. The Visa/PDOL-based GPO path is a disclosed, deliberately unimplemented gap (the no-PDOL baseline was the required scope). **Step 3 (a real contactless payment card) has not yet been run** — this is the next work immediately after this documentation lands, not a silently-abandoned gap.

**Task 24 (NFC tag emulation, Listen Mode) — code-complete, independently reviewed, real-hardware verification still outstanding.** RFID2 (MFRC522-class) cannot do this at all — a hard silicon limit, its real command set has no target/emulation mode. The NFC unit's ST25R3916 does support it (a real Passive Target Anticollision hardware state machine, confirmed in ST's vendored RFAL source, answerable entirely over polled I2C with no IRQ pin needed — the same substitution already used for the reader path). Implemented as `listen_start()`/`listen_poll()`/`listen_stop()` in `st25r3916_driver`, wired as an "Emulate" action on a saved tag's library entry, read-only UID/SAK/ATQA emulation only (full memory-content emulation, i.e. answering RATS/READ, remains a disclosed stretch goal). Independent review verified the PT-memory/MODE-register/EOF-re-arm logic byte-for-byte against the real cited source and found and fixed one latent MODE-register mask inconsistency (currently harmless, but would have silently corrupted the MODE register under a future om-encoding change). **Step 4 (a real external NFC reader, e.g. a phone) has not yet been run** — same status as Task 13: next work, not abandoned.

**RF433 bruteforce (Task 8) has a disclosed, unresolved cross-donor encoding discrepancy.** Bruce's Chamberlain timing entry is (confirmed by independent review) actually Holtek's bit timings pasted under a different name — no pilot, wrong bit encoding entirely — while Flipper/UniGeek's real Chamberlain decoder expects a structurally different 4-bit-symbol DIP-code scheme. Chamberlain-generated bruteforce candidates likely won't be recognized by this project's own decoder or a real device's actual wire format. Flagged for real-hardware testing to resolve, not fixed. Task 8's own real-hardware checkpoint (against a real fixed-code device) has also not yet been run.

**RF433's 25ms burst-gap capture threshold partially or fully clips three brands' real signal structure** (Chamberlain's 35-43ms sync window, and parts of Nice FLO/Linear) — a real, disclosed limitation of Task 5's already-shipped, twice-reviewed capture logic, documented rather than fixed since revisiting it would mean re-touching already-hardware-verified capture code.

**IR receive ("IR Learn", Task 17) is raw pulse capture only — NEC/RC5/Sony protocol decode is explicitly out of scope**, a deliberate descope from the spec's original "receive/decode" wording once real-hardware timing-threshold tuning was judged not warranted for this pass. The existing `.ir` file format infrastructure already supports raw-signal captures without decode, so this doesn't block IR Learn's SD-save/playback usefulness.

**Battery HAL has no presence-detection for this board** (inherited gap from the M5Unified reference this project ported from, which has presence-detection for other chip targets but not ESP32-P4/Tab5) — a device running on USB power alone with no pack attached can display a plausible-but-meaningless percentage.

**The GPIO53 arbiter's claim/release model is session-scoped, not reference-counted.** Safe today because exactly one screen at a time ever claims each owner value, but a future second NFC/RFID2 screen calling `ensureExternalI2CBegun()` independently of `nfc_read.cpp`'s single teardown/release point could have its claim dropped by a different session's release. Flagged for whoever adds a second such screen.

**`docs/phases/phase-3-progress-handoff.md` is now fully superseded** by this document and should be deleted or clearly marked stale — flagged to the controller, not done here per this task's own scope.

## How to build, flash, and use

```bash
cd firmware/tab5 && pio run -t upload --upload-port <tab5 serial port>
```

Host-native tests (protocol decode, file-format round-trips, crapto1 math, NEC encoding — everything that doesn't need real silicon): `cd firmware/tab5 && pio test -e native` (45/45 passing as of this document).

Serial-debug bring-up triggers exist behind `-DQUARKY_SERIAL_DEBUG` for several of this phase's spikes (RF433 edge capture, ST25R3916/WS1850S chip-ID reads, IR TX/RX presence tests) — see `main.cpp`'s `#ifdef QUARKY_SERIAL_DEBUG` block for the current key bindings.

**Hardware note, load-bearing for anyone working on this phase's code:** NFC unit, RFID2 unit, RF433R, RF433T, and the IR unit are all mutually exclusive on the Tab5's single physical HY2.0 PORT.A connector — only one is physically plugged in at a time, swapped by hand. `hal/gpio53_arbiter.{h,cpp}` coordinates *software* ownership of the shared GPIO53/54 pins across whichever unit is connected; it does not (and cannot) detect which physical unit is actually present. NFC/RFID2 use `Wire1` at I2C addresses 0x50/0x28 respectively; RF433 uses raw digital I/O on GPIO53; IR uses the RMT peripheral on GPIO53 (TX) and GPIO54 (RX).

**IR sample content note:** the real, full Flipper-IRDB community database used to build/verify Task 18 lives at `/quarky/ir/flipperdb/` on the SD card (not part of this repo) — the folder-by-folder navigator (`features/ir/ir_clone.cpp`) is rooted at `/quarky/ir` generally, one level above that prefix, so a future sibling category folder is browsable too.

## Verification: Definition of Done walkthrough

Per the design spec's Section 5 (as corrected 2026-08-19), each item below is evaluated against real task results and, where applicable, real hardware evidence actually recorded in the ledger.

**1. NFC unit and RFID2 unit both independently confirmed working for baseline tag read (UID + type), each via its own real chip driver (ST25R3916 / WS1850S respectively).**
**PASS.** Task 4 built the two drivers-and-shared-UI; real-hardware checkpoint (2026-08-20) read the same physical tag on both units and cross-checked the UIDs identical: RFID2 reported `[nfc-read] RFID2 tag: MIFARE 1KB UID AB:46:66:FA` (via `VersionReg (0x37) = 0x15`, matching Task 3's original readback exactly); the NFC unit reported `[nfc-read] NFC tag: ISO14443A SAK 08  UID AB:46:66:FA` (via `IC identity (reg 0x3F) = 0x2A → ic_type=0x28, ic_rev=2`, matching Task 2's original readback exactly) on its first-ever real-silicon attempt. RFID2 was separately confirmed against a second real tag (a MIFARE Ultralight, UID `04:D3:73:D1:3D:02:89`) during the Task 10 checkpoint.

**2. RFID2 unit's frequency capability confirmed and the 125kHz feature row resolved (implemented or explicitly dropped with a note).**
**MET, independent of on-hardware silicon testing** (this item is explicitly a datasheet question per the spec's own text). Task 3 Step 3 confirmed from primary sources — M5Stack's own Unit RFID2 documentation ("Operating Freq: 13.56MHz") and NXP's MFRC522 datasheet rev 3.9 — that neither NFC-family unit has any LF hardware; the 125kHz/T5577/HID-Prox row is explicitly dropped in the spec, and the originally-cited donor source for it (Bruce's `rfid125.cpp`) was itself found to be a UART-based external LF module driver, not a 13.56MHz-chip capability at all. Task 14 (the plan's own conditional 125kHz task) was resolved without separate implementation as a direct consequence.

**3. MIFARE key recovery succeeds against a known-weak test card.**
**PASS.** Task 9 hardware checkpoint (2026-08-21): dictionary attack recovered Key A = `FFFFFFFFFFFF` (the real factory-default key) on all 16 of 16 sectors of a real MIFARE Classic 1K test card (UID `D1:D3:4E:07`). Nested, static-nested, and parity-oracle-dictionary attacks were smoke-tested against the same card (expected to find nothing new, per the plan's own framing, since every sector's key was already known from the dictionary run) and all completed or cancelled cleanly with correct messaging and no crashes.

**4. RF433R's receive pin hypothesis (GPIO53) confirmed or refuted via a real interrupt/timer-driven test; RF433 scan, replay, and bruteforce all verified against real 433MHz hardware you own.**
**PASS for the pin hypothesis and for scan/replay; bruteforce NOT yet real-hardware-verified.** Task 1 confirmed `TAB5_RF433R_PIN = GPIO53` via a real interrupt-driven capture showing structured, repeating burst timing from a real 433MHz transmitter. Task 5 (scan) passed against real ambient RF433 traffic and deliberate remote presses, including its truncation and overrun safety paths firing correctly under real load. Task 6 (replay) passed end-to-end: a replayed captured signal actually triggered a real remote-controlled device, including correct handling of a truncated real capture. **Task 8 (bruteforce)** is implemented, independently reviewed, and build-verified, but its own real-hardware checkpoint (against a real fixed-code device) has not yet been run, and a real, disclosed Chamberlain protocol-encoding discrepancy between its two donor sources remains unresolved pending that test.

**5. Tag/signal library save-and-reload round-trips correctly from the Tab5 UI.**
**PASS.** Task 10 hardware checkpoint (2026-08-20/21): a real tag scanned on RFID2, saved via a "Save to Library" button, reappeared in and loaded correctly from the NFC Tag Library screen, confirmed by the project owner. RF433's equivalent SD interop (Task 21/22, extended live during the RF433 hardware session) was separately confirmed: a live capture saved as a real Flipper `.sub` file was then successfully browsed to and loaded via "Load from SD," fixing a real directory-cap collision bug (shared folder with thousands of pre-existing diagnostic `.raw` dumps) found in the process.

**6. IR unit's chip/protocol identified once in hand; TV-B-Gone, receive/decode, universal-remote clone, and jammer all verified against real IR remotes/devices.**
**PASS, with one disclosed scope narrowing on "decode."** The IR unit's real identity (M5Stack "Unit IR" SKU U002 — plain GPIO transceiver, IRM-3638T receiver, not I2C as originally assumed) was confirmed via a real, supplied datasheet and real-hardware GPIO-level presence tests (Task 15). TV-B-Gone (Task 16) passed against a real LG TV after a real carrier-polarity bug was found and fixed via a three-way cross-donor comparison. IR receive (Task 17, "IR Learn") passed on real hardware across nine real capture cycles including a real SD save — but is **raw pulse capture only**; NEC/RC5/Sony-level protocol decode was explicitly descoped from this pass (the spec's literal "receive/decode" wording is only partially met — capture works, bit-level decode does not exist). Universal-remote clone (Task 18) passed against the real, full on-SD-card Flipper-IRDB community database, including real NEC/NECext protocol encoding cited against Flipper's own firmware source, after two real crashes (an LVGL memory-pool exhaustion and an O(N²) directory scan) were found and fixed via dedicated investigation. The jammer (Task 19) passed — real, visible, erratic IR LED flicker confirmed by the project owner.

### Work beyond the original Definition of Done

Three tasks were added to the plan after the spec's original six DoD items were written and are not individually named by any of them. Their real status, stated plainly:
